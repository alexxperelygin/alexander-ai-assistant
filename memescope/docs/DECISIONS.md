# Decisions (ADR)

Формат: контекст → решение → последствия. Решения принимались автономно в рамках
задания; помечено, что легко пересмотреть.

## ADR-1. SQLite по умолчанию, PostgreSQL в production

Контекст: задание предпочитает PostgreSQL; MVP должен запускаться одной командой в
любом окружении (включая среды без Docker-демона).
Решение: Prisma + SQLite (`file:./dev.db`) для dev/research; схема без
SQLite-специфик (JSON — строками, без enum), миграция на PostgreSQL — смена одной
строки провайдера (инструкция в ARCHITECTURE).
Последствия: нулевой порог входа; для 24/7 production рекомендуется переключение.
Пересмотр: тривиален.

## ADR-2. Без Redis/BullMQ в MVP

Контекст: очередь нужна при масштабировании, но добавляет инфраструктурную зависимость.
Решение: worker — отдельный процесс с интервал-циклами; движки — чистые функции,
поэтому перенос в BullMQ не требует их изменений.
Пересмотр: при росте числа сканируемых токенов или необходимости нескольких воркеров.

## ADR-3. Бесплатные публичные API как ядро данных

Контекст: система должна работать сразу, без ключей; платные источники недоступны.
Решение: GeckoTerminal (discovery) + DexScreener (market) + RugCheck (risk) +
Jupiter (исполнимость). Все проверены живыми запросами. Birdeye/Helius — опциональные
адаптеры, активируются ключом в .env.
Последствия: нет глубокой истории и полных holder-метрик — честно отражено в
confidence и ROADMAP.

## ADR-4. Sell-quote Jupiter как анти-honeypot проверка

Контекст: главный катастрофический риск — невозможность продать.
Решение: перед READY система запрашивает реальный маршрут token→SOL; отсутствие
маршрута или impact сверх лимита — hard rejection.
Последствия: расход rate-лимита Jupiter (≈2 вызова на кандидата) — компенсируется
батч-лимитом кандидатов на цикл.

## ADR-5. Forward-testing вместо выдуманной истории

Контекст: честный backtest требует исторических данных, которых бесплатно нет.
Решение: система накапливает собственные снапшоты и тестирует сигналы на них;
до накопления выборки backtest возвращает NO_DATA, а не сфабрикованные метрики.
Последствия: первые недели метрик не будет — это фича честности, не баг.

## ADR-6. Live trading жёстко отключён на уровне кода

Решение: `saveRiskSettings`/`getRiskSettings` принудительно ставят
`liveTradingEnabled=false`; «live»-позиция в системе — это только трекинг сделки,
которую пользователь совершил сам и подтвердил кнопкой "I bought".
Пересмотр: только после подтверждённого out-of-sample edge и явного решения владельца.

## ADR-7. Пороговые значения выбраны эвристически

top10>60%, insiders>30%, minLiq $10k, возраст 20 мин–7 дней, стоп −35%,
TP 1.5x/2x/4x, READY≥65 и т.д. — стартовые значения из общих соображений о
микроструктуре мем-рынка, «не подтверждено данными» указано в SCORING_MODEL.
Пересмотр: обязателен после накопления датасета (train/val/test).

## ADR-8. Социальный модуль — явная заглушка

Контекст: официальный X API дорог; скрапинг нарушает ToS и запрещён заданием.
Решение: в MVP учитывается только наличие сайта/соцсетей (вес 0.1), компонента
подписана как заглушка; полный модуль (Farcaster/X) — в ROADMAP.

## ADR-9. Автономные значения по умолчанию вместо блокирующих вопросов

Контекст: сессия автономная; задание просило задать только архитектурно-важные вопросы.
Решение: выбраны консервативные дефолты (капитал $1000, риск 1%/сделка, позиция ≤$50),
все редактируются в Settings; открытые вопросы владельцу перечислены в итоговом отчёте.

## ADR-10. Данные до 5 августа 2026 считаются смещённым режимом

Контекст: до включения follow-up-слотов сканер доопрашивал в основном
«интересные» токены, поэтому исход через 6ч был измерим почти только у выживших.
Базовая линия на тех данных выглядела как медиана +2.5% и 57% прибыльных;
после включения доопроса та же метрика оказалась **−93.7% и 13% прибыльных**.

Решение: `deploy/research.mts` разделяет наблюдения по границе `UNBIASED_FROM`
и, набрав достаточно чистых данных, считает все выводы только по ним. Смешивать
режимы запрещено — это даёт оптимистичную базовую линию и ложный edge.
Пересмотр: границу двигать только при новом изменении логики сбора данных.

## ADR-11. Rug rate считается от измеримых исходов, baseline — из окна сигналов

Контекст: rug rate в отчёте вырос с 2% до 10%, и это легко принять за ухудшение
отбора. Две методические ошибки мешали проверить: (1) сигналы без forward-данных
попадали в знаменатель rug rate как «не ругнувшиеся», то есть потеря токена из
виду улучшала метрику; (2) baseline брал первые 2000 токенов из БД без сортировки
и окна, то есть самые старые — стратегия сравнивалась с другим периодом рынка.

Решение: `rugMeasurable` исключает неизмеримые сигналы из знаменателя; baseline
берётся равномерной подвыборкой токенов, впервые увиденных в интервале сигналов.
Ожидаемый эффект: rug rate вырастет ещё — это не регресс, а снятие разбавления.

## ADR-12. Отток ликвидности — жёсткая отбраковка

Контекст: искали, чем объяснить рост rug rate. Данные чистого режима (6 августа,
N=32 213 наблюдений) дали ответ на оба вопроса сразу.

Во-первых, rug rate не вырос: в смещённом режиме 5.3%, в чистом 9.1%. Обвалы
ликвидности не участились — их стало видно, потому что сканер начал доопрашивать
умирающие токены. Это ожидаемое следствие ADR-10, а не регресс фильтров.

Во-вторых, нашёлся признак, доступный ДО входа: падение ликвидности более чем на
5% между соседними опросами даёт медиану −92.5% и 7% прибыльных (n=127) против
базовых −1.4% и 42%. Эффект сохранился и на train (−96.7%), и на test (−62.1%),
coverage не завышен (54% против базовых 49%).

Решение: `liqTrendPct` добавлен в FeatureVector (считается только по собственным
прошлым наблюдениям, разрыв > 2ч → null), правило `liquidity-draining` запрещает
вход. Правило отбраковочное: оно не обещает прибыли, оно убирает категорию,
которая почти всегда теряет почти всё.

Не сделано намеренно: веса скоринга НЕ переписаны. Момент-правило
«ликв>50k И Δ1ч>+20%», которое на смещённых данных выглядело лучшим (+19.3%,
63% прибыльных), на чистых данных даёт медиану −17.4% при 50% ругпуллов.
Преимущество не подтвердилось — значит менять веса не на чем.

## ADR-13. Мультичейн: данные со всех сетей, сигналы — только там, где проверяем контракт

Контекст: Solana даёт ~40k наблюдений в сутки. До дедлайна 15 августа этого мало,
чтобы уверенно отличить edge от шума, а DexScreener и GeckoTerminal покрывают
Base, BNB Chain, Ethereum и Arbitrum теми же запросами.

Решение: реестр сетей в `src/lib/chains.ts`; discovery опрашивает каждую сеть
отдельным запросом (ошибка одной не лишает данных остальные); `Token.chain`
входит в уникальный ключ вместе с адресом, потому что один и тот же адрес
контракта существует в разных EVM-сетях.

Ограничение зафиксировано в коде, а не в намерениях: RugCheck и Jupiter работают
только с Solana, поэтому для остальных сетей нет проверки эмиссии, заморозки и
honeypot. Правило `no-contract-risk-source` запрещает таким сетям выдавать сигнал.
Они дают данные для исследования — и только. Снимается это добавлением
risk-провайдера для EVM, а не ослаблением правила.

## ADR-14. GoPlus Security закрывает проверку контрактов в EVM

Контекст: ADR-13 оставил Base, BNB Chain, Ethereum и Arbitrum в режиме «только
данные», потому что проверять контракт было нечем.

Решение: GoPlus Security (бесплатно, без ключа) даёт honeypot, доп-эмиссию,
остановку переводов, налоги, концентрацию и блокировку LP. Выбор источника
проверки идёт по сети: RugCheck для Solana, GoPlus для EVM, `null` если сеть
неизвестна — роутер никогда не выдаёт «проверку», которой не было.

Остаётся разница, зафиксированная отдельным правилом: в EVM-сетях нет
симуляции продажи через агрегатор (Jupiter — только Solana). Поэтому там
действует `sell-not-verified`: вход разрешён, только если проверка контракта
ЯВНО подтвердила, что токен продаётся. Молчание источника подтверждением не
считается.

## ADR-15. Бюджет оценки делится между сетями по очереди

Контекст: после подключения четырёх EVM-сетей discovery стал приносить ~20 новых
пулов из КАЖДОЙ сети за цикл. Очередь «никогда не оценённых» токенов сортируется
по свежести, поэтому EVM-токены вытеснили бы Solana почти полностью — а Solana
единственная сеть, где выход проверяется симуляцией продажи, а не только
проверкой контракта.

Решение: `roundRobinByChain` раскладывает очередь по сетям по очереди, сохраняя
порядок внутри каждой. Ни одна сеть не может забрать весь бюджет цикла.

Проверено на живых данных перед выкладкой: у части новых EVM-пулов DexScreener
ещё не отдаёт пары (отсюда мигание AVOID ↔ DATA_UNAVAILABLE — данные то есть, то
нет), а GoPlus для реальных токенов отвечает определённо (`is_honeypot = "0"`),
то есть EVM-сигналы возможны, а не заблокированы навсегда.

## ADR-16. X подключается точечно, а не сплошным потоком

Контекст: владелец готов оплатить X API. Соблазн — «слушать твиттер 24/7».
Арифметика против: базовый тариф это ~10 000 постов в месяц, ~330 в день, а
токенов система видит около 20 000 в сутки. Сплошной опрос сжёг бы лимит за
часы и не дал бы данных ни по одному токену.

Решение: соцданные снимаются только с токенов, уже прошедших отбор (CANDIDATE
и READY), не чаще раза в час на токен, поиском по адресу контракта. Расход
ограничен явным месячным бюджетом; при исчерпании пишется снимок с ошибкой,
а не тихий перерасход.

Уточнение после регистрации: аккаунт оказался на модели **pay-per-use**
(баланс кредитов), а не на фиксированном тарифе. Поэтому добавлен ещё и
ДНЕВНОЙ потолок: при оплате по факту месячного лимита мало — ошибка в логике
или всплеск кандидатов способны выжечь баланс за сутки, и узнаем мы об этом по
нулю на счету. Дневной предел ограничивает цену такой ошибки одним днём.

Собирается не только число упоминаний, но и возраст аккаунтов с охватом —
иначе накрутка неотличима от интереса. В скоринг ничего не добавляется до
проверки предсказательной силы: правило то же, что и для всех признаков.

## ADR-17. Сохранённая настройка перекрывает дефолт — пороги мигрируются явно

Контекст: порог ликвидности был поднят 10k → 50k по результатам исследования,
изменён в `DEFAULT_RISK_SETTINGS`, задокументирован и «выкачен». На сервере он
не действовал: в БД лежала запись настроек с 10 000, а сохранённое значение
перекрывает дефолт. Обнаружено по строке в отчёте — «Ликвидность $3 ниже
минимума $10,000» вместо ожидаемых $50,000.

Решение: `applySettingsMigrations()` в `settings.ts`, выполняется при старте
воркера. Каждая миграция помечена ключом и применяется один раз — осознанные
изменения владельца в Settings не затираются, — а факт применения пишется в
audit log вместе со старым и новым значением.

Урок общий: правка значения по умолчанию не меняет поведение системы, у которой
уже есть состояние. Проверять надо по отчёту сервера, а не по коду.

## ADR-18. Лимит скорости источника может быть шире ключа здоровья

Контекст: discovery по шести сетям получал HTTP 429; Robinhood не отработал
НИ РАЗУ (0 успехов на 161 попытку). Причина в моей же правке: ключ ограничения
скорости совпадал с ключом здоровья, а он стал разным для каждой сети —
поэтому шесть запросов уходили залпом, каждый со своим «пустым» счётчиком.
Лимит GeckoTerminal при этом общий на весь API.

Решение: в `HttpOpts` добавлен `throttleKey` — здоровье считается по сети,
скорость ограничивается по источнику целиком. Слот времени резервируется ДО
ожидания, иначе параллельные вызовы прочитали бы одно и то же значение и снова
ушли залпом.

## ADR-19. Три социсточника, каждый со своим ключом и своей честной дырой

Reddit и Farcaster подключены рядом с X. Каждый включается независимо: нет
ключа — источник просто не используется, остальные работают.

Что каждый НЕ умеет, зафиксировано в коде через `null`, а не спрятано:
* Reddit не отдаёт ни подписчиков автора, ни возраст аккаунта без отдельного
  запроса на каждого автора — охват и «свежесть» остаются неизвестными;
* Neynar в результатах поиска не отдаёт дату регистрации аккаунта — доля
  свежих аккаунтов неизвестна;
* X отдаёт и охват, и возраст, но стоит денег и ограничен квотой.

Ни один из них не подставляет ноль вместо «не знаем»: ноль означал бы
«ботов нет», а это утверждение, которого данные не поддерживают.

Секреты доставляются тем же путём, что и ключ X: секрет GitHub → по stdin в
файл с режимом 600 вне репозитория → оттуда в `.env`. Значение не печатается
ни на одном шаге и не проходит через чат.
